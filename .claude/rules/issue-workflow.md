# Issue ワークフロー

**以下は強制的な行動指示であり、例外なく従うこと。**

作業の計画・進捗は GitHub Issue で管理する。旧来の `.steering/`（requirements / design / tasklist）運用は廃止した。Issue に記載する **Definition of Done（DoD）チェックリスト** が tasklist の代替となる。

コードの変更を伴う指示を受けた場合、**コードを1行も書く前に**以下を実行すること:

1. **対応する Issue を確認する** — 既存 Issue があればそれを使う。なければ新規に起票する
2. **Issue に DoD チェックリストを記載する**（後述「DoD の記載先」「DoD テンプレート」参照）
3. **記載後すぐに実装へ着手する**（DoD についてユーザーの事前承認は不要。レビューは PR とマージ確認で行う）
4. 実装の進行に合わせて DoD のチェックボックスを `[x]` に更新する
5. 実装完了後、`.claude/rules/definition-of-done.md` の全フェーズを確認する
6. ユーザーにマージ可否を確認し、承認後にマージ・クリーンアップを行う

## DoD の記載先

| Issue の起票者 | 記載先 |
|--------------|-------|
| 自分（オーナー / Claude が依頼を受けて起票） | Issue **本文** に `## Definition of Done` セクションとして記載する |
| 他者（外部ユーザーの報告・bot の自動起票など） | 報告本文は編集せず、**コメント** として DoD を追記する |

- 進捗更新は DoD を記載した場所（本文またはそのコメント）を編集して行う。新しいコメントを積み増さない
- 1 つの Issue に DoD は 1 つだけとする。方針変更で作り直す場合は既存の DoD を編集する

## DoD テンプレート

DoD は「その Issue 固有の完了条件」と「共通 DoD への参照」で構成する。共通項目（ktlint / build / test 等）の本文は `definition-of-done.md` が正本なので、Issue には再掲しない。

```markdown
## Definition of Done

### 受け入れ条件
- [ ] <ユーザーから見て満たすべき振る舞い（再現手順が直ること等）>

### セクション 1: <マージ可能な単位の名前>
- [ ] <実装項目>
- [ ] <テスト項目（回帰テスト・新規テスト。免除する場合は理由を併記）>
- [ ] <ドキュメント同期項目（不要なら「対象なし」と明記）>

### 共通
- [ ] `.claude/rules/definition-of-done.md` Phase 3（コミット前検証）を通過
- [ ] マージ確認済み
```

### セクション分割

**以下は強制的な行動指示であり、例外なく従うこと。**

DoD のセクションは **「マージ可能な単位」** に対応させること:

- 1 セクション = 1 機能 + 対応テスト + 該当ドキュメント = 1 コミット（可能なら 1 PR）
- 各セクションが独立にビルド・テストを通過し、`main` にマージできる粒度にする
- セクション間の依存（例: A が B の前提）は DoD の冒頭で明記する
- 全セクション完了を待たずに、緑になったセクションから順に push できる構成にする

**理由:** usage limit や PC クラッシュで長セッションが中断されるケースが頻発しており、半端な状態のまま停止することを避ける。**緑のコミットを刻むほうが、巨大な未完成ブランチより回復しやすい**。

## Issue とコミット・PR の紐付け

- PR 本文には `Closes #<番号>`（または `Fixes #<番号>`）を記載し、マージ時に Issue が自動クローズされるようにする
- コミットメッセージの書式は `.claude/rules/git-conventions.md` に従う（Issue 番号の付与は任意）
- 作業ブランチ名は `.claude/rules/git-conventions.md` の命名規則に従う

## 調査・リサーチタスク

コード変更を伴わない調査は、Issue に調査結果をコメントとして記録する。リポジトリへのコミットは不要。永続的に参照すべき結論は `docs/` に反映する（`.claude/rules/documentation.md` 参照）。

## 例外

Issue 起票を省略してよいケースは → `.claude/rules/definition-of-done.md` の「例外（フェーズ横断の免除マトリクス）」の「Issue 省略」列を参照すること（定量基準: 3ファイル以下 / 50行以下 / 新規クラスなし / 新規EPなし / public API不変。典型例: タイポ修正・1行の設定変更・コメント追加・定数値修正）。

## git worktree 運用

コード実装は **Claude Code のビルトイン worktree 機能**で隔離して行うこと。メインリポジトリでは Issue の確認・起票のみ行う。

### worktree 作成前の必須前処理

**以下は強制的な行動指示であり、例外なく従うこと。**

`EnterWorktree` を呼び出す **前に**、メインリポジトリで必ず以下を実行する:

```bash
git fetch origin
git log --oneline origin/main..HEAD   # ローカル main が origin より進んでいないか確認
git log --oneline HEAD..origin/main   # ローカル main が origin より遅れていないか確認
```

- ローカル `main` が `origin/main` より遅れている場合は、`git pull --ff-only origin main` で同期してから worktree を作成する
- 同期せずに worktree を切ると、stale な HEAD 上で実装が進み、後から再マージが必要になる

### worktree 作成と運用

- **単一機能:** `EnterWorktree` ツール（または `claude --worktree <機能名>`）を使用する。worktree は `.claude/worktrees/<機能名>/` に作成され、ブランチ `worktree-<機能名>` が HEAD から自動生成される。セッション終了時に自動クリーンアップされる（変更ありの場合は確認プロンプト）。
- **並列実装:** 各ウィンドウで `claude --worktree <機能名>` を使用する。各ウィンドウは担当 Issue を 1 つだけ持つ。
- **手動 worktree は使わない:** `git worktree add ../rescript-wt-*` による手動作成は非推奨。ビルトイン機能を使うこと。
- **編集パスを必ず確認する:** worktree に入った直後に `pwd` と `git rev-parse --show-toplevel` を実行し、編集対象が worktree 内のパスであることを確認する。メインリポジトリ側に誤って編集を反映させた事例があるため、最初の Edit/Write の前に確認すること。
- **クラウドセッション:** 作業ブランチがあらかじめ指定されている環境（Claude Code on the web 等）では、worktree を作らず指定ブランチで作業してよい。

## 実装完了後のマージ確認

DoD のすべてのチェックボックスが `[x]`（マージ確認項目を除く）になり、ビルドが成功したら、以下の手順でマージを進める:

1. `AskUserQuestion` ツールでマージ可否を確認する
   - 実装の概要・変更ファイル数・対象 Issue 番号を提示する
   - セキュリティに影響する変更がある場合、その旨を明示する
   - ユーザーの承認を待つ（承認なしにマージしない）
2. 承認後、DoD の「マージ確認済み」を `[x]` に更新し、「worktree マージ・クリーンアップ手順」に従ってマージする
3. マージ完了後、セッションを終了する（worktree の自動クリーンアップを発動させる）

## worktree マージ・クリーンアップ手順

worktree 内での実装が完了し、`main` にマージする際は以下の順序で実行する。**順序が重要** — マージ前に worktree を削除すると変更が失われる。

```bash
# 1. worktree 内で main にマージ
git checkout main
git merge <作業ブランチ>

# 2. 作業ブランチを削除
git branch -d <作業ブランチ>
```

マージ後は **セッションを終了する**。worktree のクリーンアップはセッション終了時に自動で行われる。

**重要:** 同一セッション内で `git worktree remove` を手動実行してはならない。シェルの CWD が削除済みパスを指し続け、以降の Bash コマンドがすべて失敗する。

## CWD が壊れた場合の復旧

worktree 削除や `git worktree remove` により CWD が無効になった場合:

1. **現在のセッション内では Bash コマンドが使えない**（CWD が存在しないため）
2. `Task` ツール（サブエージェント）を使用して、メインリポジトリのパスを CWD に指定して操作する
3. または、現在のセッションを終了し、新しいセッションをメインリポジトリで開始する

## 残存 worktree の手動クリーンアップ

メインリポジトリの新しいセッションで以下を実行する:

1. `git worktree list` で残存 worktree を確認する
2. 残存があれば `git worktree remove <path>` で削除する
3. マージ済みブランチを `git branch -d <name>` で削除する
4. `.claude/worktrees/` 内の残存ディレクトリを `rm -rf` で削除する
