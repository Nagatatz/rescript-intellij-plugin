# 自動化プレイブック

長時間・反復的な作業を自律ループや並列スワームで回すためのレシピ集。**実装は未着手**であり、本ファイルは「将来発火する仕掛けの仕様書」として保持する。実際に走らせる前に、各レシピの「事前確認」と「ガードレール」を必ず満たすこと。

---

## 1. Type Coverage 自動上昇ループ

### 目的

`coverage/` 機能（Type Coverage Heat Map）と Kover の `minBound` ラチェット（`.claude/rules/release.md`）を組み合わせ、低カバレッジファイルへ段階的にテストを追加していく自律ループを定義する。

### 適用条件

- 直近のリリースで Kover 実測カバレッジが目標値（例: 85%）に到達していない
- 純粋関数中心のパッケージが対象（UI / LSP 結合クラスは免除対象）
- usage limit による中断耐性が必要な長時間作業である

### ループの構造

1. `./gradlew test koverHtmlReport` を実行し、`build/reports/kover/html/index.html` を解析する
2. パッケージ単位のカバレッジを抽出し、`testing.md` の **免除対象** に該当しないものを昇順に並べる
3. 上位 1 ファイルを選び、対象クラスのソースと既存テストを `Read` する
4. 未カバーのブランチに対するテストケースを `<クラス名>Test.kt` に追加する
5. `./gradlew test` を実行し、最大 5 回までテスト側だけを修正してグリーンにする
6. グリーンになったら `✅ Add tests for <クラス>` でコミット
7. 進捗を `.claude/coverage-progress.json` に保存（処理済みファイル一覧、現在のカバレッジ %）
8. 目標未達なら次のファイルへ。10 コミットごとに PR を起こしてユーザーに確認を仰ぐ

### ガードレール

**以下は強制的な行動指示であり、例外なく従うこと。**

- **本体コードを変更してテストを通してはならない。** テスト側でしか修正しない
- `testing.md` の免除対象（Swing UI、LSP 結合、IDE ライフサイクル等）を選ばない
- `main` への直接 push は禁止。10 コミットごとに PR を起こす
- 進捗ファイル `.claude/coverage-progress.json` をコミットに含めない（`.gitignore` 対象）
- セッションが usage limit で停止しても、進捗ファイルから次回再開できる構造を維持する

### キックオフプロンプト例

```
Type Coverage 自動上昇ループを起動する。
前提:
  - 目標: line coverage 85%
  - 対象パッケージ: util/, lang/, indexing/
  - 免除: testing.md の免除対象すべて
  - 進捗ファイル: .claude/coverage-progress.json
ベースラインを取り、上位 20 ファイルを提示してから 1 件ずつ着手する。
10 コミットごとに stop し、PR を起こすこと。
```

## 2. テンプレート並列実装スワーム

### 目的

Wizard の 21 テンプレート（および将来の追加分）に対して、**N 個の独立した worktree でサブエージェントを並列に走らせ**、最後にコーディネーターが整合をとってバッチ PR を起こす運用を定義する。

### 適用条件

- N 件の独立した実装タスクがあり、各タスクが他タスクのコードに依存しない
- 各タスクのスコープが揃っている（テンプレート 1 件 + 対応テスト + EN/JA docs）
- 各項目に 1 つずつ GitHub Issue が起票済み（または起票可能）である（`issue-workflow.md` 参照）

### ワークフロー

1. ユーザーから N 件の作業項目リストと共通設計制約を受け取る
2. メインリポジトリで `git fetch origin && git pull --ff-only origin main` を実行
3. N 件分の Issue を起票し、各 Issue に DoD を記載する（Issue 番号は GitHub が採番するため衝突しない）
4. 各項目について次を実行:
   - `EnterWorktree` で `.claude/worktrees/template-<key>/` を作成
   - サブエージェントに「実装 → テスト → EN/JA docs → コミット → DoD 更新」を一気通貫で依頼
   - 各サブエージェントは自身に割り当てられた Issue のみを扱う
5. 全エージェント終了後、コーディネーターが各ブランチで `./gradlew clean buildPlugin test` を実行し、緑のものから順に PR を作成
6. 失敗ブランチはダッシュボード（テキスト出力）で報告し、ユーザーに対応方針を確認

### ガードレール

**以下は強制的な行動指示であり、例外なく従うこと。**

- 共有ファイル（`plugin.xml`、`CLAUDE.md`、`README.md`、`docs/repository-structure.md`）への変更は **コーディネーターのみ** が行う。サブエージェントに直接編集させると衝突する
- Issue と DoD を用意してから着手する。Issue なしの並列着手を禁止する
- 各 worktree は `git fetch origin` 実施後の最新 `origin/main` から作る（`issue-workflow.md` の「worktree 作成前の必須前処理」を必ず遵守）
- 失敗ブランチのコードを **強制マージしない**。コーディネーターは緑のブランチのみ PR 化する
- 全 PR を一括 squash merge する場合でも、コミット粒度は機能単位を保つ（`git-conventions.md` 参照）

### キックオフプロンプト例

```
テンプレート並列実装スワームを起動する。
作業項目:
  1. <template-key-1>: <概要>
  2. <template-key-2>: <概要>
  ...
共通制約:
  - validation library 選択は既存 17 テンプレートの既定に揃える
  - EN/JA docs 同時更新（sphinx-po-ja-sync 参照）
  - 共有ファイル編集はコーディネーター集約
N 件分の Issue を起票し、DoD を記載してから着手する。
全 worktree 完了後、緑のブランチについて PR を作成し、ダッシュボードで集計報告する。
```

## 共通の運用ルール

- **セッションごとに 1 プレイブックのみ起動する。** Coverage ループとテンプレートスワームを同時に走らせない
- 進捗ファイル（`coverage-progress.json`）は **コミットしない**。ローカル状態として扱う
- usage limit や PC クラッシュからの復旧時は、必ず進捗ファイルを先に読み、二重実行を避ける
- 自律ループに入る前に、ユーザーから「開始してよい」明示的な合図を得ること。本ルールは仕様書であり、自動発火を許可するものではない
