# Audit タスク規約

リポジトリ横断の **audit / 棚卸し / カバレッジ調査** タスクは、サブエージェント単発の出力を真に受けず、**二段検証** を必須とする。

## 対象タスク

以下のような「網羅性」を主張する作業は本ルールの対象:

- API カバレッジ調査（`@tauri-apps/api` 全 API のうち何件実装済みか、等）
- テンプレート監査（21 テンプレートの整合性、欠落項目の洗い出し）
- ロードマップ精査（`docs/product-requirements.md` 未実装機能の再分類）
- ドキュメント完全性レビュー（CLAUDE.md / README.md / sphinx-docs の同期チェック）
- リファクタリング候補の抽出（重複コード、deprecated 利用箇所の総ざらい）
- 依存関係インベントリ（`build.gradle.kts`、`package.json`、ロックファイルの突合）

## 必須プロセス

**以下は強制的な行動指示であり、例外なく従うこと。**

### Step 1: 一次調査（Task agent 利用）

- `general-purpose` または `Explore` エージェントに調査範囲を明確に渡す
- 調査範囲・対象ファイル・判定基準を **プロンプト内で明示する**（「曖昧なら null と返せ」と指示する）
- 出力は「項目リスト + 各項目の根拠（ファイルパス + 行番号）」の形式で受け取る

### Step 2: 二次検証（独立クロスチェック）

一次調査の結果をそのままユーザーに報告してはならない。以下のいずれかで **独立に裏取り** すること:

1. **ランダムスポットチェック:** 一次結果から 5 件を無作為抽出し、本人が `Read` / `grep` で原典を確認する
2. **逆方向走査:** 「実装済みリスト」が出たら「未実装の理由を 1 件選んで証明する」など、対称な検索を別途実行する
3. **第二エージェント:** 異なる検索戦略（例: 一次が grep ベースなら二次は import 解析）で別エージェントを走らせ、件数・主要項目を突合する

矛盾が見つかった場合は、**矛盾そのものをユーザーに報告し**、追加調査の方針を確認する。差を黙って埋めない。

### Step 3: 報告の書式

ユーザーへの最終報告には以下を含めること:

- 一次調査で発見された総数と方法
- 二次検証で行ったクロスチェックの内容（「5 件スポットチェックして全件一致」「件数が ±1 だったので原因を特定済み」など）
- 残存する不確実性（「サブモジュール内は調査範囲外」など）

**不確実性が残っているのに「完了」と宣言してはならない。**

## 反パターン

- 一次調査の結果をそのまま `## 結果` として貼って終わり
- 「およそ N 件」「ほぼ全部」など定量化せずに完了宣言
- 二次検証を「コードを読みました」程度の曖昧な記述で済ませる
- エージェント出力にあった `TODO` やプレースホルダーを真の値として扱う

## 適用しないケース

- 単一ファイル内の調査（grep 一発で済む）
- 既知の小さなリストの再確認（例: `docs/` 直下の md ファイルを 1 つずつ読む）
- ユーザーが明示的に「ざっくりでいい」と指示したケース

これらは Task agent の二段検証ではなく、直接 `Read` / `grep` で済ませて良い。
