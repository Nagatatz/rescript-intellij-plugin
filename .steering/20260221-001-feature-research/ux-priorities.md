# UX 優先度分析 — ReScript IntelliJ Plugin

## 1. UX 設計の基本原則

### 1-1. 「IDE が邪魔をしない」原則

最も重要な UX 原則は、**IDE がユーザーの作業を中断しないこと**。具体的には:

- **フォールスポジティブの最小化**: 不正確な警告やエラーは信頼を損なう。表示するなら正確でなければならない
- **不要なポップアップの抑制**: コメント・文字列内での補完ポップアップは作業の妨げ（→ Completion Confidence の重要性）
- **ノイズの排除**: `node_modules/` 内のエラー、長行警告、インジェクション内の誤検出を抑制

### 1-2. 「期待通りに動く」原則

JetBrains IDE ユーザーは他の言語（Java, Kotlin, TypeScript）で習得したショートカットとワークフローをそのまま使いたい:

- **Ctrl+W** (選択拡大) → ReScript の言語構造に沿って動作すべき
- **Ctrl+Shift+J** (行結合) → `let` バインディングやパイプチェーンを賢く結合すべき
- **Ctrl+U** (Goto Super) → `.res` → `.resi` へのジャンプに対応すべき
- **Ctrl+Shift+T** (Go to Test) → テストファイルへの移動・生成が動作すべき
- **Alt+Enter** (Intention) → 適切な修正候補が表示されるべき

### 1-3. 「見つけやすい」原則

機能は**ユーザーが探す場所に存在**すべき:

- Generate メニュー (Cmd+N) に Switch Arms / Module Type / Make Function 生成
- Refactor メニューに Pipe ⇔ 関数呼び出し変換
- Navigate メニューに .res/.resi/.js 間の移動手段
- 右クリックコンテキストメニューに Run/Debug/Test
- Settings > Languages & Frameworks > ReScript に設定

## 2. ユーザージャーニーに基づく優先度マトリクス

### 2-1. 新規プロジェクト開始（頻度: 低、影響: 大）

ユーザーが ReScript プロジェクトを初めてセットアップする際の体験。第一印象を決定する。

| ステップ | 現状 | 理想 | 関連機能 |
|---------|------|------|---------|
| プロジェクト作成 | Project Wizard あり (12テンプレート) | **実装済み** | `RescriptModuleBuilder` |
| LSP セットアップ | インストール通知あり | **実装済み** | `RescriptLspStartupActivity` |
| 初期ファイル作成 | File Template あり | **実装済み** | `RescriptCreateFileAction` |
| rescript.json 編集 | JSON Schema あり | **実装済み** | `RescriptJsonSchemaProviderFactory` |

**評価**: 新規プロジェクト体験は**十分にカバー済み**。

### 2-2. 日常的なコード編集（頻度: 最高、影響: 最大）

最も頻繁に行われる操作。ここの品質が全体の印象を決める。

| 操作 | 現状 | 不足 | 優先度 |
|------|------|------|--------|
| 型の確認 | hover + Expression Type あり | パイプチェーンの中間型が見えない | **A** |
| 補完 | LSP 補完あり | コメント/文字列内の誤ポップアップが残りうる | 実装済み |
| エラー確認 | 診断 + Error Lens あり | 型ミスマッチの expected/actual が分かりにくい | **B** |
| パイプ操作 | 基本的な入力のみ | Pipe ⇔ 関数呼び出し変換がない | **S** |
| switch 操作 | arms 生成あり | ケース統合がない | **A** |
| コメント操作 | 行/ブロックコメントあり | `%raw()` 内のコメント切り替えが不正確 | **A** |
| 未使用警告 | reanalyze あり | 未使用結果に `->ignore` の Quick Fix がない | **S** |
| ブロック整理 | Unwrap あり | 冗長 `{ expr }` の自動検出がない | **S** |

### 2-3. コードナビゲーション（頻度: 高、影響: 大）

大規模プロジェクトでの探索効率に直結。

| 操作 | 現状 | 不足 | 優先度 |
|------|------|------|--------|
| 定義ジャンプ | LSP で対応済み | — | 実装済み |
| .res ⇔ .resi 移動 | Alt+O あり | — | 実装済み |
| テストファイル移動 | Go to Test あり | — | 実装済み |
| 使用箇所検索 | Find Usages あり | — | 実装済み |
| シンボル検索 | Go to Symbol あり | — | 実装済み |
| .resi 宣言管理 | — | 公開/非公開の切り替えがない | **A** |

### 2-4. リファクタリング（頻度: 中、影響: 大）

コード構造の改善。高品質な IDE の差別化ポイント。

| 操作 | 現状 | 不足 | 優先度 |
|------|------|------|--------|
| リネーム | LSP 連携あり | — | 実装済み |
| Import 最適化 | Ctrl+Alt+O あり | — | 実装済み |
| Surround With | Ctrl+Alt+T あり | — | 実装済み |
| 分割代入導入 | なし | 頻出パターンの自動化 | **B** |
| React コンポーネント抽出 | なし | ReScript React では高需要だが高難度 | **C** |

### 2-5. コード生成（頻度: 中、影響: 中〜大）

ボイラープレートの自動化。手動記述の退屈さを軽減。

| 操作 | 現状 | 不足 | 優先度 |
|------|------|------|--------|
| Switch arms 生成 | Cmd+N あり | — | 実装済み |
| Module type 生成 | Cmd+N あり | — | 実装済み |
| Make 関数生成 | なし | レコード型のコンストラクタ生成 | **A** |
| JSON codec 生成 | なし | 頻出ボイラープレート | **B** |
| 型注釈一括追加 | なし | .resi 準備の効率化 | **B** |

## 3. 感情的インパクト分析

ユーザーが「このプラグインすごい」と感じるか「使いにくい」と感じるかを決定する要因。

### 3-1. Delight（感動）を生む機能

**初めて使ったときに「おっ」と思う機能**:

| 機能 | 感動ポイント | 優先度 |
|------|------------|--------|
| パイプチェーン中間型ヒント | 型推論の流れが目に見える | A |
| Pipe ⇔ 関数呼び出し変換 | Alt+Enter 一発でスタイル変換 | S |
| ラベル付き引数一括挿入 | React コンポーネントの全 props が一瞬で出る | A |
| PPX 展開ビュー | `@react.component` の裏側が見える | C |
| 識別子ケース修正 | タイポを自動検出して修正提案 | S |

### 3-2. Frustration（不満）を解消する機能

**ないと不便を感じる機能**:

| 機能 | 不満ポイント | 優先度 |
|------|------------|--------|
| 未使用結果 `->ignore` | 毎回手動で `->ignore` を追加するのが面倒 | S |
| 冗長ブロック削除 | 不要な `{}` が残るとコードが汚く見える | S |
| MultiLang Commenter | `%raw()` 内で Ctrl+/ が正しく動かない | A |
| Long Line Inspection | `@module("...")` パスで不要な警告が出る | A |
| .resi 公開/非公開 | .resi を手動編集するのが面倒 | A |

### 3-3. 基本品質（あって当然）

**ないと「壊れている」と感じる機能**:

これらは既に実装済み:
- シンタックスハイライト ✅
- コード補完 ✅
- エラー表示 ✅
- 定義ジャンプ ✅
- フォーマット ✅

## 4. 競合比較に基づく差別化

### 4-1. ReScript VSCode 拡張との比較

VSCode 拡張にあって IntelliJ プラグインにない機能:

| 機能 | VSCode | IntelliJ | ギャップ |
|------|--------|----------|---------|
| LSP 基本機能 | ✅ | ✅ | なし |
| Code Actions | ✅ | ✅ (LSP API) | なし |
| Switch arms 展開 | ✅ (LSP code action) | ✅ (Generate + LSP) | なし |
| Paste as JSON | ✅ | ✅ | なし |
| `%raw()` ハイライト | ✅ | ✅ | なし |
| コンパイルステータス | ✅ | ✅ | なし |
| フォーマット | ✅ | ✅ | なし |

**結論**: VSCode 拡張との機能的ギャップは**ほぼ解消済み**。差別化は JetBrains IDE 固有の高度な編集支援にある。

### 4-2. 他の JetBrains 言語プラグインとの比較

上位プラグイン（Kotlin, Dart, Go）が「標準」として持つ機能:

| 機能 | Kotlin | Go | Dart | ReScript | ギャップ |
|------|--------|-----|------|----------|---------|
| Pipe/Chain 型ヒント | ✅ (chain hints) | — | — | ❌ | **あり** |
| Fill named params | ✅ | ✅ | ✅ | ❌ | **あり** |
| Generate constructor | ✅ | ✅ | ✅ | ❌ | **あり** |
| Destructuring | ✅ | — | — | ❌ | **あり** |
| Implement interface | ✅ | ✅ | ✅ | ❌ | **あり** |
| Parameter Info (Ctrl+P) | ✅ | ✅ | ✅ | △ (LSP) | **部分的** |
| Unused result quick fix | ✅ | ✅ | ✅ | ❌ | **あり** |

## 6. 実装ロードマップの推奨

### Phase 1: Quick Wins + Frustration 解消
- 未使用結果 `->ignore` Quick Fix
- 冗長ブロック削除 Inspection
- 識別子ケース修正
- Long Line Inspection Policy
- MultiLang Commenter

### Phase 2: 生産性向上
- Pipe ⇔ 関数呼び出し変換
- Make 関数生成
- Switch ケース統合
- インターフェース公開/非公開

### Phase 3: 差別化
- パイプチェーン中間型ヒント
- ラベル付き引数一括挿入
- JSON エンコーダ/デコーダ生成

### Phase 4: 関数型言語固有の差別化（Haskell/F#/Scala 調査から）
- 常時型表示パネル（Sticky Type Info）
- デコレータ/属性補完 (@genType, @module 等)
- .resi シグネチャ同期
- ケースの変数分割（Case Split）
- レコードスタブ生成
- 演算子優先順位のホバー表示

### Phase 5: 高度な機能
- React コンポーネント抽出
- PPX 展開ビュー
- モジュールタイプ実装生成
- 型ミスマッチ差分表示（Fine-grained Type Diff）
- Worksheet モード

## 7. 関数型言語 UX の特別考慮事項

### 7-1. 型推論中心の開発ワークフロー

関数型言語プラグイン（Haskell, F#, Scala）の調査から、**型推論が強力な言語では型の可視化がユーザー体験の核**であることが明確になった。

ReScript に特に重要な教訓:

| 教訓 | 具体例 | 対応する機能 |
|------|-------|-------------|
| 型は「見えない」のが最大の不満 | パイプチェーンの中間結果の型がわからない | 常時型表示パネル, パイプチェーン型ヒント |
| 型エラーは「どこが違う」かが重要 | `expected array<string> got array<int>` の差分 | 型ミスマッチ差分表示 |
| 型で関数を探したい | 「string → int の関数は？」 | 型シグネチャ検索（将来） |
| 型から正しい値を提案してほしい | `option<'a>` が期待される場所で `Some(x)` を提案 | 型ホール支援（将来） |

### 7-2. パターンマッチ中心の開発ワークフロー

Haskell と Scala の調査から、パターンマッチングに関する IDE 支援の重要性が浮き彫りになった:

- **Case Split**: 変数を全コンストラクタに展開（Haskell Wingman の最人気機能）
- **ケース統合**: 同じボディのケースをまとめる（Gleam）
- **網羅性チェック UI**: 不足ケースの一括挿入（既に LSP code action で部分対応）

### 7-3. シグネチャファイルの管理

F# の `.fs`/`.fsi` ペアは ReScript の `.res`/`.resi` ペアと完全に同構造。F# エコシステムの以下の機能は直接移植可能:

- **宣言をシグネチャに追加** (FsAutoComplete: AddBindingToSignatureFile)
- **シグネチャの値を更新** (FsAutoComplete: UpdateValueInSignatureFile)
- **パラメータ名の同期** (FsAutoComplete: RenameParamToMatchSignature)

これらは ReScript の `.resi` 管理で最も頻繁に必要とされる操作。

### 7-4. REPL / インタラクティブ評価

Haskell (GHCi), F# (F# Interactive), Scala (Worksheet) すべてがインタラクティブ評価を IDE に統合している。ReScript にはネイティブ REPL がないため:

- **短期**: コメント内評価（HLS eval plugin 方式）が最もライトウェイト
- **中期**: Worksheet モード（コンパイル→Node.js実行のパイプライン構築）
- **長期**: ReScript コンパイラへの REPL 機能リクエスト
